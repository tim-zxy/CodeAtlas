# P05-W3-001 Java Parser and Symbol Extraction Design

Date: 2026-09-25
Task: P05-W3-001
Status: written design for user review; implementation is not authorized by this document

## Purpose and authority

Establish the first real Native Analyzer language path: given an approved Java SourceFile inventory, the Rust process parses the current source bytes and emits stable, source-grounded Java symbol Provider Facts, diagnostics, and coverage through existing Native IPC v1. Success is demonstrated by the declared `java-basic-symbol` and `java-nested-types` Fixtures, protocol and security failure tests, and the existing Phase 0.5 Critical Symbol Recall gate of at least 95 percent. This task does not activate a Canonical Graph or complete Phase 0.5.

The controlling authorities are [WORK_BREAKDOWN](../../handoff/WORK_BREAKDOWN.md), [PHASE_ACCEPTANCE](../../handoff/PHASE_ACCEPTANCE.md), [DESIGN_TRACEABILITY](../../handoff/DESIGN_TRACEABILITY.md), [Native IPC](../../handoff/specs/NATIVE_IPC.md), [Canonical IR](../../handoff/specs/CANONICAL_IR.md), [Provider SPI](../../handoff/specs/PROVIDER_SPI.md), [Runtime Configuration](../../handoff/specs/RUNTIME_CONFIGURATION.md), [Security](../../handoff/specs/SECURITY.md), [Evaluation](../../handoff/specs/EVALUATION.md), [ADR-014](../../handoff/adr/ADR-014-multilanguage-native-analyzer.md), and [Native Analyzer Scalability](../../specs/native-analyzer-scalability.md). This design adds no FROZEN schema change or new numeric Quality Gate.

## Existing baseline and chosen architecture

The current Rust binary serves one strict `DESCRIBE` request and does not yet parse Java or handle `ANALYZE`. The TypeScript IPC schemas already define strict `ANALYZE` requests, Provider Fact events, coverage, diagnostics, terminal counts, and checksums; the production Native client already validates complete byte streams and accepts process arguments. `Repository` already carries `rootPath`, while SourceFiles carry repository-relative paths and fingerprints. Runtime code currently implements only bootstrap configuration, not the planned indexing worker setting. The existing client collects a complete bounded response in memory; this is not a large-repository streaming-to-staging implementation.

Add a Rust internal `LanguageAnalyzer` boundary. The Native coordinator validates the request, obtains eligible source bytes, enforces budgets, schedules bounded work, and emits IPC records. The Java adapter owns Tree-sitter grammar setup, syntax traversal, Java symbol classification, source ranges, and syntax diagnostics. Framework meaning remains in Plugins; recognizing an annotation's syntax does not infer Spring or other framework semantics. Rust never writes Canonical SQLite and never assigns Canonical IDs.

Use one bounded Rust scheduler for file parses, with one parser instance per worker. This is preferred over multiple Node-launched analyzer processes, which would duplicate process/protocol accounting, and over adding a worker field to strict IPC v1, which would change an already frozen wire contract. The scheduler has bounded pending, in-flight, and completed-but-unconsumed work; it does not collect every AST or event for the entire repository. The fact emitter drains in deterministic source-file and fact order while honoring stdout backpressure. Stderr is diagnostics-only; stdout contains JSONL protocol records only. The Phase 0 byte-stream client hard ceilings remain intact and are not raised to claim large-repository support. Streaming normalization and SQLite staging belong to their separately assigned tasks.

## Inputs, worker configuration, and source safety

The sole requested parse-worker mode is `EffectiveConfig.indexing.nativeAnalyzer.parseWorkers`: `AUTO` or an explicit positive safe integer. P05-W3-001 introduces only the minimal validated process-local indexing configuration and launch path needed for this task; it does not require Phase 1 YAML loading or another user-facing knob. The control plane resolves an effective worker count against available execution resources and the request's `maxMemoryBytes`, records requested and effective values, and rejects an impossible explicit request before analysis. A private Native process argument conveys only the validated effective count; Rust checks it against the request budget again. `DESCRIBE` without arguments keeps its existing behavior. Default count, per-worker reservation, and memory policy must be justified by pinned measurements during implementation planning; this document does not invent them.

The analyzer takes its only repository root from the existing `ANALYZE` payload's `repository.rootPath`, not from a second launch argument. At the process-local access boundary it validates that locator, joins only validated repository-relative SourceFile paths, and prevents ancestor/final-component symlink or reparse-point escape. It reads only requested eligible Java text SourceFiles, checks file identity and current raw-byte fingerprint against the supplied observation, and treats disappearance or change as `SOURCE_CHANGED`, never as an empty successful parse. For this Git-only phase, use the established raw-byte `sha256:` observation policy where that fingerprint is supplied; the Canonical IR fingerprint type itself remains opaque. No source bytes enter routine logs or error messages.

## Output contract and deterministic identity

The adapter extracts package declarations, classes, interfaces, methods, fields, constructors, and nested types. It emits ProviderNode records using the existing provider ID, ProviderSnapshot/Repository/Revision identities, Java-specific `providerKind`, name, qualified name where determinable, confidence, and SourceRange. SourceRange remains zero-based, start-inclusive/end-exclusive with UTF-8 byte columns. A package declaration or symbol with no safe range must use the contract's explicit nullable range rather than invent coordinates. Provider Fact IDs use `java-symbol-v1:` plus lowercase SHA-256 of unambiguously length-prefixed UTF-8 fields: repository-relative file path, symbol kind, lexical owner chain, simple name, source-spelled declaration signature for methods/constructors, and the ordinal among otherwise identical declarations in that lexical scope. The ordinal follows source order, not worker completion order. A move within a file that preserves those fields does not change identity; a rename, signature change, or file move may. Exact IDs and ranges are pinned by Fixtures. This distinguishes duplicate declarations without guessing semantic equivalence or assigning Canonical IDs.

The coordinator emits `ANALYSIS_STARTED`, requested `SOURCE_FILE` observations, zero or more `NODE`, `COVERAGE`, and `DIAGNOSTIC` events, then exactly one legal terminal event. This task emits no inferred `EDGE` merely to populate the stream. It maintains contiguous sequence numbers, context agreement, exact terminal counts, event/byte budgets, and a checksum over the exact pre-terminal JSONL bytes required by IPC v1. Source-file and fact output order is deterministic even if parses finish out of order. Successful zero-fact analysis is distinct from failure. Syntax-error files may yield source-grounded partial symbols plus explicit diagnostics and `PARTIAL` coverage/outcome; they must not yield invented resolved relations. Unsupported language/capability and untrusted source access are reported distinctly using existing error/coverage channels where applicable. Only a completely validated `SUCCEEDED` or `PARTIAL` terminal stream can be considered for later state application; an incomplete or failed stream cannot.

## Scope and dependency boundary

P05-W3-001 covers Java symbol extraction, its language boundary, minimal validated worker configuration, bounded parsing/emission, source safety, and its two declared Fixtures. Normal/static/wildcard imports, direct/constructor calls, extends/implements, type/method/field references, ambiguity preservation, and unresolved targets are P05-W3-002. The complete per-capability outcome matrix and coverage statistics are P05-W3-003. File-level REFRESH and add/modify/delete graph changes, normalization, SQLite batch activation/rollback, full Worker Consistency, and cold/1-/5-/50-file performance baselines retain their assigned later Phase 0.5 tasks. This task may include a small different-worker/different-completion-order regression test for its own Provider Facts, but it does not claim the full normalized Canonical Graph and stale-state phase gate.

No Python or additional framework implementation, Spring interpretation, AST persistence, adaptive scheduler, new IPC v1 field, new ProviderSnapshot field, new Canonical IR schema, or Knowledge/Wiki path is introduced. If exact Java extraction needs a FROZEN contract change, stop for an ADR or Design Change Proposal before implementation. EVOLVABLE resource policy changes require pinned Fixture/Evaluation evidence and synchronized documents.

## Fixtures, failures, and acceptance

Create version-1 Evaluation manifests for `java-basic-symbol` and `java-nested-types` with pinned Java source trees and exact expected ProviderNode identities, kinds, names, qualified names, UTF-8 byte ranges, per-file coverage, and diagnostics. Basic cases include package/class/interface/method/field/constructor facts; nested cases distinguish nested classes/interfaces and duplicate names in different scopes. An adapter-boundary test proves annotations are syntax only and do not emit framework facts. Fixture declarations must use the existing registry schema and existing Critical Symbol Recall threshold; no new numeric accuracy or performance threshold is introduced.

Focused tests cover `AUTO`, valid explicit, invalid, and budget-impossible worker inputs; different completion orders yielding identical ordered Provider Facts and coverage; stdout/stderr separation and downstream backpressure; source change, symlink/reparse escape, invalid request, syntax-error partial output, and successful zero-fact output. They exercise protocol counts, checksum, terminal integrity, timeout/cancellation, event/byte ceilings, and no exposed partial applicable result. Tests for the complete P05-W3-003 outcome taxonomy and full P05-W9-001 Worker Consistency are not relabeled as this task's acceptance.

The implementation plan must identify the executable Fixture runner and exact expected-artifact format before coding. On completion, run focused Rust and TypeScript tests, both registered Fixtures and the applicable Critical Symbol Recall gate, full repository build/test/architecture/format gates, and failure/recovery checks. Record commands, results, versions, worker configuration and measured resource evidence, limits, and remaining Phase 0.5 gaps in `CURRENT_STATUS.md`; update `DESIGN_TRACEABILITY.md` with actual Fixture and test paths. Hosted clean-install CI must be observed before integration is called complete.
