# P05-W3-003 Coverage and Outcome Design

Date: 2026-09-28
Task: P05-W3-003
Status: written design for user review; no product implementation is authorized by this document

## Intent and authority

Make the Java analyzer's per-file, per-capability coverage measurable without mistaking an honestly unresolved relation for a missing fact or a failed analysis for an empty success. The denominator is a source-grounded syntax site that the adapter actually recognized for the requested capability. Syntax that cannot be inspected because parsing failed is not silently added to, or omitted from, a claimed complete denominator: the file is marked `PARTIAL` with a diagnostic. Success requires exact registered coverage/outcome Fixtures, strict cross-language protocol validation, visible limitations in a read-only summary, and no applicable result from a failed stream. This task alone does not complete Phase 0.5.

The controlling authorities are `docs/handoff/WORK_BREAKDOWN.md` P05-W3-003, `PHASE_ACCEPTANCE.md`, `DESIGN_TRACEABILITY.md`, `specs/NATIVE_IPC.md`, `specs/PROVIDER_SPI.md`, `specs/EVALUATION.md`, `specs/AGENT_API.md`, `specs/CANONICAL_IR.md`, ADR-010/012/014, and `docs/specs/native-analyzer-scalability.md`. The merged P05-W3-002 Java relation path at `9bd70cf75802f0b344cc5aa2d437db83375a8ccf` is the implementation baseline. The proposed compatible wire extension is separately recorded as [ADR-015](../../handoff/adr/ADR-015-native-ipc-v2-coverage-statistics.md); it must be accepted before code changes that emit or accept protocol v2.

## Existing behavior and choice

Native IPC v1 has a strict `COVERAGE` payload with `capability`, `sourceFileId`, `support`, and `coverage`; its completed terminal carries aggregate states but no site counts. The Java adapter returns facts, diagnostics, and complete/partial syntax coverage. The coordinator emits one coverage event per requested file/capability and already distinguishes successful zero-fact analysis, syntax-error partial success, budget/resource failure, unsupported language/capability, and internal parser failure through existing terminal/diagnostic channels. The TypeScript client validates event order, counts, checksum, byte limits, and the complete terminal before releasing a result. There is no Phase 0.5 graph query or SQLite activation to extend in this task.

Deriving counts only from emitted facts cannot find recognized sites that produced no fact. Encoding numbers in diagnostic text would make the statistics unvalidated prose. The chosen design preserves v1 and adds a separately negotiated IPC v2 `COVERAGE` shape with typed site statistics. There is no ProviderSnapshot v1 change, Canonical IR change, migration, new language, or new numerical Quality Gate. The descriptor will advertise both supported protocol versions; the existing v1 handshake Fixture's expected version list must be deliberately reviewed and updated, while its framing, schema, error, and raw-byte corpus remain valid.

## Versioned contract and data flow

`DESCRIBE` advertises protocol versions `[1, 2]` and IR schema `[1]`. A v1 `ANALYZE` request receives the unchanged v1 event shapes; a v2 `ANALYZE` request receives the v2 envelope and a strict v2 `COVERAGE` payload. Rust never mixes protocol versions within a stream. TypeScript validates the response against the request's version, including the existing request-ID, sequence, context, count, checksum, line/event/total-byte, terminal, cancellation, and failure rules. An unsupported version fails explicitly. The current hard byte/event ceilings are not raised; a statistics-bearing stream that cannot fit fails with the existing resource error rather than dropping coverage records. The one-shot process need not persist negotiated state.

Each v2 `COVERAGE` record retains the v1 fields and adds `statistics` with non-negative safe-integer `eligibleSites`, `coveredSites`, `unsupportedSites`, `partialSites`, and resolution counts `EXACT`, `HEURISTIC`, `AMBIGUOUS`, `UNRESOLVED`, `UNSUPPORTED`. The exact names and strict JSON shape are normative for the implementation plan, subject to ADR acceptance. `eligibleSites = coveredSites + unsupportedSites + partialSites`. For a relation capability, the five resolution counts sum to `coveredSites`; for `SYMBOL`, they are all zero. Counts never use floating-point ratios as a substitute for exact integers. The language-neutral TypeScript validator checks these cross-field equations and uniqueness of `(sourceFileId, capability)` coverage within the requested scope; Java Fixture/Evaluation checks prove that the counts correspond to emitted source-grounded facts. Synthetic compilation-unit and package-container nodes are excluded from site counts. Terminal NODE/EDGE event counts remain wire counts and need not equal site counts.

The Java adapter records one eligible site for each recognized declaration or requested relation occurrence, including distinct declarators within one declaration. A site is `covered` when it produces its intended source-grounded ProviderNode or ProviderEdge. A relation whose target is `AMBIGUOUS`, `UNRESOLVED`, or `UNSUPPORTED` remains covered if its honest edge was emitted; its target level is counted separately. A recognized construct outside the adapter's supported extraction set is `unsupported` and emits no fabricated fact. A recognized but malformed/incomplete construct that cannot be safely emitted is `partial`. Each site has exactly one of those three coverage dispositions; the first-pass declaration index does not double-count sites observed again in the emitting pass. Syntax-error regions that the parser cannot enumerate are unknown, not zero; the affected file/capability retains `PARTIAL` coverage and a source-grounded diagnostic even if its known-site counts balance. An entirely valid empty file has zero counts and `COMPLETE` coverage.

The coordinator emits exactly one v2 coverage record for each requested, supported file/capability, in stable source-file and request-capability order. The capability-level terminal observation remains the existing conservative aggregation: any partial file makes that capability partial. A v1 response has no numeric site statistics; a consumer reports `statisticsAvailable: false` rather than interpreting missing fields as zero. A small pure TypeScript coverage-summary function operates only on a fully validated success result and produces per-file/capability counts, resolution distribution, and warnings for partial, unsupported, unresolved/ambiguous, or unavailable statistics. It does not query SQLite, activate graph state, or implement `understand`/`trace`; P05-W5-001 and P05-W8-001 must carry these warnings into their future responses.

## Failure and security behavior

Keep the existing closed terminal error codes: `BUDGET_EXCEEDED` for deadline/timeout, `RESOURCE_LIMIT_EXCEEDED` for admitted memory or output exhaustion, `UNSUPPORTED_LANGUAGE` and `UNSUPPORTED_CAPABILITY` for unsupported requests, and `INTERNAL_ANALYZER_FAILURE` for parser exception/panic. They must remain distinguishable from `SUCCEEDED` with zero facts and from a completed `PARTIAL` syntax result. Unknown requested capabilities or an unsupported language may fail the request rather than manufacturing zero-valued per-file statistics. Failed, cancelled, corrupt, over-budget, or inconsistent streams expose no applicable coverage summary or graph result. Diagnostics are bounded and must not include unrestricted source or secrets. Rust stdout remains JSONL-only, stderr remains diagnostic-only, and Rust retains no SQLite authority.

## Fixtures and verification

Add registered P05-W3-003 Fixture manifests with pinned Java source, exact provider facts, v2 coverage/diagnostic goldens, and expected terminal outcome for: mixed resolved/heuristic/ambiguous/unresolved relations; recognized unsupported source context; syntax-error partial coverage; and valid zero-fact success. A fixture containing synthetic import-container nodes proves site counts do not equal raw NODE counts. At least one mixed file proves the eligible-site partition and resolution-distribution equations exactly. Existing Java SYMBOL and relation Fixtures continue to pass on v1 without changing their Provider Facts. Any existing DESCRIBE golden whose advertised version list changes receives an explicit reviewed baseline update, not a silent rewrite.

Add shared Rust/TypeScript protocol-v2 valid and invalid byte cases for version mismatch, missing/extra/duplicate coverage, negative/non-integer/overflow counts, partition or resolution-sum mismatch, checksum/count mismatch, post-terminal data, and v2 payload sent under a v1 envelope. Real-binary tests prove v1/v2 negotiation, exact output, unchanged failure recovery, and identical coverage statistics under one and two workers with deliberately different completion orders. Parser-exception and timeout/budget paths use deterministic Rust fault injection or unit seams rather than a production fault flag. The pure summary tests prove that v1 statistics are unavailable, not zero, and that incomplete or unresolved coverage creates explicit warnings. Evaluation reports these distributions without creating an unapproved numerical threshold; the Phase 0.5 critical symbol/call gates remain unchanged.

Run the declared TypeScript/Rust unit and integration tests, fixture registry/goldens, formatting, builds, architecture guardrails, and hosted clean-install CI. Record exact commands, fixture IDs, pass counts, any schema version change, and residual limits in `CURRENT_STATUS.md`; synchronize the Native IPC, Provider SPI, Evaluation, Phase Acceptance, and Design Traceability documents with accepted ADR-015 before treating implementation as done.

## Explicit exclusions and governance

No REFRESH, changed-file invalidation, Canonical normalization/FactMerger, SQLite apply, graph query, CLI `understand`/`trace`, framework semantics, Knowledge/Wiki/Diagram/Agent consumption, or full cold/1-/5-/50-file benchmark belongs to this task. No numeric latency or coverage threshold is invented. If an implementation result conflicts with the accepted versioned contract, stop for a reviewed design amendment rather than weakening a Fixture or treating missing statistics as a complete zero.
