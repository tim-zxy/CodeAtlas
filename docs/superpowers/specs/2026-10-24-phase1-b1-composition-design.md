## 4. B1-A：可独立实施的纯组合契约（拟议）

### 4.1 输入、身份与声明

拟新增一个 package-private Providers 模块，具体签名/文件和命令在书面方向接受后由 writing-plans 固定。没有 public index 导出，没有 Application/Runtime/Store 调用者。

输入职责：

- 严格 Source target 三元组、完整**声明** inventory、预先分配的一份 Native snapshot identity、Provider/tool 版本声明与组合开始/结束时间。全部只是声明，不能认证磁盘或执行。
- Java v2 的完整 parsed request/events/terminal，重新使用原 strict schema 与 normalizeNativeAnalysis 校验；不接受仅凭 TypeScript 类型标记为 validated 的对象。第一单元不新增 Java 字节 decoder，不声称有 Java 原始 request checksum。
- v5 的原始 request/output bytes，调用既有 validateCodeSyntaxObservationStream；不得把 v5 改写成 v4 消息，也不得复用 v4 owner-context 函数假装已验证 v5 捕获权限。
- 显式读取/对象/序列化限制；不得新设默认值、放宽 hard cap 或把预算数字当新 profile。先检查真实字节长度和安全数据，再复制/解析；组合必须计入各输入及结果的重叠，不仅逐个限制子输入。

完整 inventory 必须唯一、严格匹配 SourceFile；Java 请求清单等于 Java 投影，v5 清单等于本次 Java/Python 观察投影。两者每个共享文件的全部字段精确相同。出现未支持但被声明为本次分析范围的 Source，明确拒绝；不能从 inventory 静默过滤以宣称全仓完整。

Java 子结果仅在 Java 投影非空时必需；无 Java 时为显式 null，不能放一份伪造成功终端。v5 仍必需，包括空清单场景，以验证明确的空结果。空仓仅得到声明空候选，没有实际仓库为空的证明。

单个 operation 在生成请求前分配一份 snapshot ID；所有原始 Provider facts 的 providerId/providerSnapshotId/repository/revision 均须匹配。不同 ID 直接拒绝，禁止接收后重写 facts。Provider/runtime/tool 版本声明必须一致；pure 检查不认证对应二进制或同一运行。

### 4.2 成功条件与一份 snapshot

Java 若存在，必须原契约 SUCCEEDED；v5 必须整体 SUCCEEDED，Python Code 必须 COMPLETE（无 Python 时 NOT_APPLICABLE），Syntax 必须 COMPLETE。任一 PARTIAL/FAILED/CANCELLED、失败结算或缺失组件均不可产出可组合成功候选。保留原观察及局限，不把 Code/Syntax 拆成两个半发布结果。

特别地，已有 class、wildcard、动态/损坏 Source 场景可能诚实地产生 PARTIAL；本单元的成功路径不消除这些限制，也不意味着这些 Source 已达到产品可用条件。

输入同时包含每个组件声明的 startedAt/settledAt 时间记录及组合时间窗口，均由上游声明：开始不晚于任何子运行开始，完成不早于任何子运行结算；纯接口校验时间次序和包含关系，不认证时钟或真实运行。没有真实时间证据时，输出明确保持声明性质；不得由输出文件 mtime/当前时间补造。

拟议组合 capability 使用三个明确限定的名称：`JAVA_CODE_V2`、`PYTHON_SYNTAX_CODE_V1`、`FRAMEWORK_SYNTAX_OBSERVATION_V1`。这些是待批准的 capability 名称，不是新 wire 或性能门槛。只为存在的语言投影列前两项，Syntax 项对应完整声明的原始语法观察，不能据此声称已有框架语义、ExecutionGraph 或 BusinessFlow。各项 SUPPORTED/COMPLETE 只在该固定 scope 的全部义务成功时成立，不发出泛化 Python SYMBOL/REFERENCE 完整声明。旧 descriptor/协商与 capability 名称原样保留；将来任何消费此新 scope 的生产入口必须显式识别，否则拒绝。

组合 snapshot 通过既有 ProviderSnapshotSchema 验证；原诊断内容按既有 schema 验证，组件身份放在独立的组合来源记录中；不得向原 message 追加前缀而突破已有长度限制，也不能把 Source/path/异常原文拼进错误。没有组件伪造另一个 Provider，也没有第二份 Native observation 进入 merger。

### 4.3 归一化、来源和返回值

Java 调用既有 Java normalizer；Python 调用 normalizePythonSourceObservation；同名 fact 或跨文件/owner/端点冲突必须拒绝，不“取第一个”。对一份组合 observation 调用既有 merger，保留既有 Evidence 构造、选择、悬空引用和冲突检查。所有新 Evidence 源于本次声明 snapshot；历史 Evidence 不参与此首单元。

返回深冻结的 **Native 投影候选**：组合 snapshot、归一化及 merger 产物、原 v5 观察与分组件来源记录、scope、请求/输出可得的完整性标识。输出明确是结构校验通过，**不包含** authenticated/ready/applicable 布尔值、capture handle、stage lease、最终 RepoBasis 或 Store 令牌。

原 v5 ownerBinding 只授权声明的旧/临时 owner-map；输出新 Python 节点形成观察内闭包。它不自动变成最终候选授权。后续必须把观察 owner 映射到完整候选的实际 node/support，最终 basis 计算后再创建 Canonical SyntaxEvidence；本单元只保留 wire Syntax，不能填旧 basis 或全零占位先创建 Canonical Syntax。

结构包和 digest 可由调用者构造，因此返回值永远不是证明真实执行的凭证。真实 owner 必须另外遵守 write_code_syntax_observation 的 settlement Err；完整 COMPLETED 字节不能覆盖 late-flush cancellation 的调用失败。本单元不让一个 caller-provided `settled=true` 产生执行权限。

### 4.4 错误与恢复

非法数据/identity/inventory、子流不完整、scope 不支持、normalization/merge 冲突、限制越界各保留可区分的固定类别；具体名称随计划列入 Fixture。消息不回显 Source、SQL、路径、环境、payload 或底层异常。失败无外部状态、无重试、无部分候选；自有内存与监听资源按 owner 收尾。输入 mutation、Proxy/getter、共享/脱离 byte view 与超大前置分配必须在计划中明确测试。
