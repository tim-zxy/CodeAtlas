## Intent, authority and predecessor evidence

Connect the existing real Rust REFRESH producer to a bounded TypeScript process/staging path and one validated Store activation transaction. A successful refresh must update the active graph and compatible restart summaries together. Failed, partial, stale or cancelled work must retain the last committed state, including historical Evidence and unrelated Provider support. Restart and retry must use the indexed baseline, not process-local caches or the last scanner delta.

R009 stores normalized candidates, not raw Provider payloads. A Canonical representative may be selected from another Provider and must never be inverted into a Native observation. ## Selected approach and non-scope

Extend the existing process client, TEMP patch stage and Store transaction with dedicated v3 entry points. Reuse Application `applyAnalysisPatch`, strict schemas, fact digests, normalizers and FactMerger selection. Storage receives structural validation ports injected by Runtime and still cannot import Providers.

Rejected alternatives: a separate summary commit can diverge from the graph on crash; replacing every refresh with full bootstrap destroys retained-support provenance and violates changed-only analysis. Neither is a fallback implementation.

Keep strict v1/v2, Canonical IR v1, ProviderSnapshot v1, summary v1 and R001-R010 unchanged. No new migration, public Provider SPI rewrite, raw-fact/AST table, extra worker setting, language/framework, optimized dependency index, adaptive scheduler, Wiki/Knowledge/Agent feature, watcher or daemon. E owns persisted differential/performance Evaluation; query and CLI remain separate tasks. D does not advertise incremental capability before the real integration and Evaluation requirements pass.

## D1 Trusted preparation and applicability

The proposed internal Runtime entry is `applyNativeRefreshAnalysisV3`. Its name and the following owner-local methods are proposed, absent APIs, not existing exports. It receives the database, validated effective execution/source-policy context, process options, descriptor, target repository/revision and a positive safe trusted memory budget. Callers do not supply an authoritative baseline bundle, SQL locator or precomputed source delta. Do not add a second public configuration setting. Use the existing validated worker configuration path.

1. Validate the trusted scalar and require the exact reviewed REFRESH_TRANSPORT profile before lazy source-inventory preparation, JSON allocation, stage construction or spawn. Scalar-only refusal has zero opener/serialization/spawn observations. A function supplied for lazy preparation is called at most once after admission. Match embedded request budget to that scalar exactly before transport.
2. Require descriptor protocol3/IR1 and the existing evaluated Java capabilities; compare actual Provider/language/resolver/normalizer/policy/capability versions with trusted effective context. A wire string alone is not proof of policy selection. Root locator and worker count are not semantic compatibility discriminators.
3. In one consistent Storage read snapshot capture the indexed pointer, bounded validated summaries, accepted activation token and complete current source inventory. The baseline expectation uses the indexed fingerprint, not the already reconciled target fingerprint. The target expectation uses current WORKTREE metadata.
4. Require the same mutable WORKTREE revision ID. Different IDs, immutable target, missing legacy R009/R010 state or semantic incompatibility return controlled `FULL_ANALYSIS_REQUIRED` before spawn. Keep the reason available as bounded metadata. Invalid/corrupt summaries or resource refusal fail closed; do not repair them, silently run full analysis or treat failure as an empty baseline. Broken R010 is not silently downgraded to legacy availability.
5. Compare baseline SourceFiles to the complete current selected inventory by normalized path, stable ID, fingerprint, role/provenance/content kind, language hint and sensitivity, using packet A's semantics. Derive sorted add/modify/delete including previous deletion identity/fingerprint; rename is delete+add. At a retained path a changed stable ID is invalid, not a guessed rename. Supply exactly this delta and the full target inventory to the request validator.
6. Reject any inventory/context drift before starting analysis. Do not use only the last ChangeDetector result: after failed Apply, a second reconciliation may be empty while indexed summaries are still old. An empty delta with a matching baseline is a valid zero-parse refresh observation; it still goes through validation and coactivation, not an inferred-current shortcut.

Complete inventory means the same selected analyzer scope used by bootstrap under the trusted source policy, not an arbitrary subset. Read its source rows/count through a Storage-owned port. No preparation step mutates source inventory, canonical rows or summaries. Source reconciliation remains a separate existing workflow.

## D2 Request preflight and streaming process

The proposed Provider entry `streamNativeRefreshV3` prepares bounded header, ordered BASELINE_SUMMARY records and REQUEST_COMPLETED with the existing packet A schema/checksum. Bound each record before building a complete string; count LF-inclusive aggregate bytes before buffering. Validate the complete owned request with packet A byte/object rules before spawn and pass the same owned bytes and trusted budget to C's decoder. Caller mutation after preparation cannot change request or context. Avoid repeated uncontrolled parse/copy/serialize passes; any unavoidable simultaneous copies belong to the measured workspace.

Use the existing process owner: absolute executable, `shell:false`, allowlisted environment, stdin drain/backpressure, stdout line decoding, bounded stderr, timeout/deadline, cancellation and bounded termination. Await each sink delivery before consuming the next event. No retained complete event array or independent unbounded async queue. The child may run concurrently with stdout staging, but no successful result is exposed until complete stdin write, stdout/checksum verification, stderr capture and acceptable child exit all settle. A success terminal followed by extra bytes, premature EOF, a late nonzero exit/write error, cancellation or timeout cannot reach Store Apply. A blocked sink must be interruptible; close its iterator/listeners and terminate the child without waiting indefinitely.

Keep ceilings: aggregate stdin and individual line1,000,000 bytes; stdout10,000,000; events10,000; stderr1,000,000. Apply lower options/request limits as well. Metadata uses these same limits; do not invent chunking or side-channel files. Existing typed Native errors remain closed; `FULL_ANALYSIS_REQUIRED` is Application applicability, not a new wire error. Process/decoder terminal is observation only. PARTIAL never becomes an applicable candidate.

## D3 Bounded TEMP stage and database-bound overlay seal

Extend `RepositoryPatchStage` for v3 statistics and complete target summaries, retaining v1 categorical coverage unchanged. Use a declared-limit constructor/entry, a separate `acceptNativeSummary` path, and a `sealNativePatchState`/`readSealedNativeState` pair with connection/context ownership. Names are proposed and may follow existing naming, but obligations below cannot be dropped.

TEMP summary columns mirror B's source ID/path/fingerprint/summary JSON and enforce unique target files. Summaries cover every target file, including unchanged and zero-fact files; SOURCE_FILE events still cover only added/modified files. Complete target coverage/statistics and diagnostics are snapshot observations, not delta-only counts. Enforce aggregate metadata and numeric SQL length/row/maximum checks before reading or parsing TEXT. Charge metadata, event/support/candidate rows, retained strings and simultaneous overlay maps; bound every iterator materialization by existing byte/count limits. Use the inherited serialized-summary limit, not an invented capacity increase. Reaching a cap refuses rather than dropping facts.

Seal order is completed observation -> provisional normalization/support preparation -> mandatory Provider-owned overlay validation -> immutable sealed stage -> Application success/context gate -> Store Apply. Like B, sealing freezes all stage writes. No normalization after seal or exposing an applicable candidate before seal. Stage close runs in finally on every path and owns only TEMP cleanup, never committed data.

The dedicated overlay validation port receives bounded iterables, not a fabricated full-only `fullStage`:

- accepted baseline header/summaries/token and complete target inventory/context;
- retained Native ACTIVE binding/Evidence/snapshot/per-support Canonical candidates through Storage-owned readers;
- actual removals/upserts and their normalized pairs/supports;
- complete target summary/header, coverage and diagnostics.

It proves all of the following before sealing:

1. Baseline union by `(factType,providerFactId)` exactly equals the applicable Native ACTIVE support identity set. One binding, matching ACTIVE Evidence and successful snapshot provenance, one schema-valid R009 candidate and correct Canonical mapping per identity; no duplicates, missing/orphan support, mixed repository/revision/Provider or dangling FactEvidence. Use the per-support candidate, not selected Canonical confidence/content from a different Provider. The stored header and token match that indexed baseline. Reject unattested retained support; neither a digest alone nor a Canonical row establishes Native applicability.
2. C's wire proof remains mandatory: removals exist, actual upsert content digests/context are valid, operations are unique, and replaying them onto the validated baseline ledger yields exactly the complete target ledger. Retained identities preserve equal content digests, while changed dependent edges may upsert without a source-file modification. References resolve through the target node union, not only delta nodes. Shared ownership is deduplicated by identity but every owner is present with equal digest and lawful package-container kind; owner transfer alone retains the existing support.
3. Bind those retained ledger identities to the actual database support view, carry the exact untouched per-support candidate forward, and validate the actual normalized delta against the target graph/reference/source view. Compare summary symbols/source ownership to the corresponding candidate projections where fields are retained. Keep old snapshot/Evidence IDs on retained support; do not relabel all target facts to the new snapshot to satisfy the full-only validator. Do not recompute Provider content digests from lossy Canonical representatives or claim an unavailable raw-payload comparison. Rust's existing semantic baseline reconstruction/check remains required before successful production output; D does not replace it with a ledger-only assertion.
4. Complete target summaries, coverage statistics and file diagnostics correspond as in B/C, including zero facts, source-less diagnostic ownership and truly run-global diagnostics. Exact target SourceFile set and metadata match the selected current inventory. Target references and final Canonical graph are valid after every proposed removal and reselection.
5. Baseline validation distinguishes historical source ranges from target applicability. A declared deleted Native source may appear in old support that this patch retires; do not reject a lawful delete simply because reconciliation already removed its source row. All retained/upserted active target ranges must still exist. If unrelated Provider support would leave a dangling active target graph, reject the patch with old state intact; never silently retire that Provider or fabricate a source/Evidence row.

These checks implement the accepted overlay obligation without raw-fact persistence or a second resolver. If Fixtures reveal the current summary/support representation cannot prove this contract, stop for an evidence-backed design amendment; do not weaken the seal or introduce a hidden full-source parse. Ledger integrity and database applicability are separate proofs.

## D4 One Store-owned activation transaction

Add proposed `RepositoryCanonicalFactStore.applyNativeAnalysisPatch(stage,expected,baselineToken)` alongside the existing legacy entry. Reuse the existing private patch transaction logic with explicit Native-only sealed-state handling; do not copy the whole writer or create a second transaction owner. Legacy calls have no sealed-state authority and keep clearing derived state on success. Failed legacy writes keep prior state.

Check sealed stage/connection/context, successful snapshot, exact baseline token and complete target metadata before `BEGIN IMMEDIATE`; recheck token, revision kind/fingerprint, count and every selected SourceFile field under that write lock, before mutation. The token includes indexed ID/fingerprint, every derived header tuple and committedSnapshotCount. A same-fingerprint legacy activation, different Provider activation, source classification drift or concurrent Native refresh invalidates the prepared candidate. No fingerprint-only guard or Runtime-only recheck is sufficient. Use the complete inventory pinned at preparation, including unchanged files; do not trust only SOURCE_FILE delta events.

Inside that single transaction:

1. Validate support baseline and delete-aware target applicability; retire only the named Native removals/upsert predecessors, with existing INVALIDATED/SUPERSEDED semantics. Preserve unrelated and unchanged support/Evidence history.
2. Append the successful snapshot once, write actual upsert Evidence/bindings/candidates, reselect affected Canonical facts using existing FactMerger rules, and validate final edges/unresolved targets/support integrity.
3. Persist complete target coverage and bounded diagnostics for the new snapshot. Older snapshot observation rows remain historical; do not use the new snapshot as the owner of all retained facts.
4. Replace derived Native state with the sealed complete target header/files within this transaction. Preserve the existing repository-wide invalidation rule for other derived headers when the graph activation changes; no unrelated stale header remains advertised as current. This clears derived cache metadata, not other Provider graph support.
5. Advance indexed ID/fingerprint, verify expected row counts and COMMIT once. Summary replacement and graph activation cannot be individually committed or retried.

Any exception rolls back graph, Evidence transitions, FactEvidence, bindings, candidates, snapshots/coverage/diagnostics, headers/files and pointer together. Tests reopen the database to prove it; an in-memory return value is not rollback evidence. Never issue R010 down migrations, delete the old graph before validation, or write persistent rows from Rust/Providers/Runtime outside Store Apply.

## D5 Admission, calibration and telemetry

REFRESH_TRANSPORT is a new internal evidence purpose covering the complete Node preparation/read/request/process/decoder/stage/normalization/overlay-seal/Apply lifetime, not just C observation verification. No concrete reservation is selected here. Keep C REFRESH_VERIFY distinct and preserve all historical profiles/raw/candidate/holdout files. Runtime consumes only explicitly approved exact-build static profiles; no startup calibration, automatic retry-until-green or dynamic widening.

Node module changes invalidate all current exact-build profiles. On the final measured implementation, run unchanged READ_SEAL and FULL_TRANSPORT compatibility corpora, unchanged REFRESH_VERIFY corpus, and the new real D-purpose corpus. Pair original purposes as already approved; calculate the new D purpose separately using the accepted high-water/range policy, exact environment/build/corpus hashes and all eligible successful and failure observations. Retain the existing five fresh-process repetitions per comparable calibration class and a complete independent one-process-per-class holdout. Missing classes, identity/hash drift or overflow refuses candidate generation. Holdout failures do not join the candidate to make it pass. Report exact proposed values and obtain separate human numeric approval before installation/admitted production acceptance.

D classes must exercise preparation near input ceiling; high retained summaries/sites/shared owners; dense actual upserts/removals and dependent edges; complete target coverage; SQL-column preflight refusal; normalization/candidate/overlay retention; delete/empty/zero-fact paths; slow stdin/stdout/sink; partial/corrupt/late-exit/cancel paths; source/token races; and transactional rollback/reopen. The implementation plan must pin exact case IDs/input recipes and class completeness before measuring, not invent measured peaks now. Synthetic fault children are permitted for lifecycle negatives; successful correctness and D-purpose execution also use the real Rust producer. No test bypass is reachable through the product API.

Keep the existing twice-actual-retained-SQL-UTF8 surcharge and numeric-before-TEXT preflight. Account the D path's newly overlapping retained SQL strings explicitly; do not count one representation twice or borrow unused full/C headroom. Preserve startup-inclusive absolute maxRSS bytes, environment and capture method. Reservation equality passes, one byte below refuses; every fresh required class peak must fit the matching approved reservation. Finite sampling is not an OS RSS guarantee or a phase performance threshold.

Record transport, normalize, Store Apply/lock, total, staged bytes, Node peak method/units, requested/effective workers and success/refusal context. Distinguish combined transport time from unavailable Native parse/resolve or child peak; mark unavailable with a reason, not zero. Full scan/parse/resolve/IPC/normalize/DB/total/peak cold/1/5/50/worker performance baseline remains E/P05-W9-001.
