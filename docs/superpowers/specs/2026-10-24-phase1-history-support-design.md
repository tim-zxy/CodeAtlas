## 4. 逻辑数据契约

### 4.1 不可变的激活历史

未来联合 Store 在一次成功提交中产生不可变 ActivationHistoryRecord（逻辑名称，非新 Canonical 核心模型/协议版本）：

- activationId、parentActivationId、repositoryId、WORKTREE revisionId；各自唯一且链关系明确，无环、跨库引用拒绝。parent 可记录同库旧 revision 的显式历史前驱，但旧 revision 的 Source/support 不得直接作为当前 revision 的 retained 成员。
- 本次最终 RepoBasis、完整历史 Source target/SourceFile 清单、repositoryLocatorDigest、提取/normalizer/契约/策略身份。Source 保留所有分类项目，包括 OTHER 和零事实文件；不是只保存 emitted facts 对应的文件。
- 本次新观察记录：唯一 Native snapshot（若该次有观察；NO_OP 不创建快照）、完整请求/输出可得的身份、声明观察 scope、实际结算/资格记录的引用；Java parsed-only reference 不变成 raw checksum。
- 有效 Code support membership、按文件/组 coverage 的来源引用、Syntax 原观察与其当前投影/支持关系。
- canonical record digest 和关系清单摘要；不能包含自身摘要字段，也不能用 root/db 路径作身份。

历史 record 的 final RepoBasis 是提交后 Code/support 状态的绑定，不用本 manifest 摘要替代 codeActivationDigest。现有 C3-A Code digest 与 owner-map 编码原样保留；历史/成员关系摘要作为**附加 CAS 读集**，其编码在具体计划/Fixture 中冻结，不能自行改既有 C3-A 摘要语义。

只有新的 validated 联合 Store 可以建立有效记录；caller JSON、文件 checksum、自洽 manifest 或 B1-A plain result 都不授予历史身份。R011 不从旧当前 Source 表猜测 backfill：没有历史就是 UNAVAILABLE。

### 4.2 Source unit 与支持 membership

Source unit = 完整 SourceFile 的历史值及其所属 repository/revision。有效性比较包括 id/path/contentFingerprint/classification(role/provenance/contentKind)/languageHint/sensitivity；任一变化都不能标 unchanged。不按文件名近似、mtime 或内容相同推断身份迁移。

每个 Code membership 指向已有的 `(evidenceId,factType,canonicalFactId,originSnapshotId,ProviderFactRef)`，以及 origin candidate 的 exact value digest、依赖 Source unit/group、契约身份和 coverage 来源。必须验证 Evidence/binding/link/R009 candidate 相互对应且原 origin snapshot SUCCEEDED。保留完整原始 candidate，不能用混合后的 winner/confidence 代替。

**Native 依赖粒度提议：**

- Python 最小 Syntax-Code 契约是逐文件依赖；从原 v5 fact/observation 的 sourceFileId 建立 membership，不从 Canonical MODULE 的 null range 猜来源。没有通用 resolver，因此不声称能保留任意跨文件解析结果。
- Java 第一版以**整个 Java 投影**为保守依赖组，覆盖 package container 等没有单文件 range 的事实。任何 Java Source 身份/相关契约变化，重新观察完整 Java 投影；Java 未变化的 Python-only 更新则保留整个旧 Java 组。不得依靠 ProviderFactId 前缀或 null range 猜单文件归属。
- 未来若要更细 Java changed-only 依赖，须另以 summary/Source/Evaluation 证明；不能把旧 Java v3 的全仓清单换成混合仓库过滤清单。本提议不替代/修改旧 v3 Java 增量路径。
- 其他 Provider 的依赖由其已验证的 membership 声明决定；没有来源依赖证明的旧支持不能猜成“不依赖 Source”。

这不增加性能门槛。保守组重算的时间/内存是否满足既有门禁仍须实际 Evaluation，未通过不得把性能问题记为已验收。

## 5. 从旧历史到目标的转换

### 5.1 捕获与差分

未来 Storage 同一有界读事务捕获：旧有效 history pointer/record、当前活动完整 Code/support 与 C3-A 基础读集、最新完整 target Source。必须证明旧 record 对应当前**活动** basis；目标 Source 可以比 indexed basis 更新。比较同 WORKTREE ID/fingerprint 仍须完整内容/支持/成员关系，不能跳过。

本版增量仅复用同一 WORKTREE revisionId 的支持；跨 revision 返回 FULL_ANALYSIS_REQUIRED，不给含旧 revision 的 Canonical ID 改标。旧历史清单按 id/path 唯一。差分互斥完备：UNCHANGED（所有 Source 字段一致）、ADDED、MODIFIED（相同 id、任一字段变化，含 path）、REMOVED（旧 id 不再出现）。rename 不自动继承：相同 id/path 的普通修改走 MODIFIED；不同 id 的改名走删除+新增。跨分区 id/path 重叠、互换等不能满足现有 wire 唯一性时，明确 FULL_ANALYSIS_REQUIRED，不放松旧解析器、不自动重试全量。

removed 的旧 id/path/previous fingerprint 必须来自捕获的旧历史；目标清单必须证明相应旧身份已退出当前 scope。Source 改为 OTHER/TEST/生成物或其他分类也不是“字节没变，所以可 retain”；范围退出/分类变化须显式重新验证，首版草案可要求完整重建，不直接伪装为物理删除。目标 SOURCE/TEST 中出现未支持语言、BINARY 或 SECRET 时保留既有 scope/安全拒绝，FULL_ANALYSIS_REQUIRED 不是读取这些文件的许可。不能向旧安全边界外的文件发请求。

### 5.2 请求和观察 scope

- Python-only 更新：只观察 added/modified 的 Python Source，保留满足完整身份/依赖/契约条件的其他 Python 文件和整个未变 Java 组。
- Java 组变化：观察全部目标 Java Code/Syntax，Python 只观察其自身 changed 文件；未变 Python membership 保留。Java v2 仍是完整 Java 投影，v5 观察清单是本次明确 scope；不得把这些 parsed/byte 子结果伪装为 B1-A 的完整 target inventory。
- B1-A composeNativeProjection **保持原样**，继续只接受完整声明投影、拒绝 removed。未来增量 assembler 是独立契约/入口，不能删除 A 的完整性检查来适配 delta。
- 只有 removals、没有新事实时，Source 历史承担删除真实性；不能假造 Native 删除观察。若进入新 Native snapshot 路径，须有按其准确 scope 正常成功结算的观察（允许协议已定义的空 sourceFiles/NOT_APPLICABLE），新 snapshot 只描述该空/局部 scope。整个激活的完整 coverage 来自经过验证的旧+新 membership，不能从空观察推导。没有真实准入/成功结算就不 Apply。
- 完全无变化且 history/当前完整 supports/Source/契约均匹配时，可返回 NO_OP 草案；实际 owner 仍需最终重查。不得凭 NO_OP 创建新 ProviderSnapshot/重采集时间或宣布 Knowledge 编译仍有效。

Source removal ledger 与完整 operation identity 绑定：旧 history digest、expected old basis、目标 Source 清单、差分、每份精确请求身份、结果身份、退役/保留 scope 全部参与。v5 requestChecksum 只覆盖原始请求，不替代这个联合 ledger；不改已接受 owner-map，不声称一个 hash 认证了来源。

### 5.3 保留、退休与选择

| 旧支持条件 | 转换 |
| --- | --- |
| 本次未观察，完整 Source/依赖组/契约仍一致 | RETAIN：旧 Evidence/binding/R009 candidate/origin snapshot ID 与采集时间保持原值；新 history 只增加当前 membership |
| 本次确实重新观察，同 ProviderFactRef 再出现 | SUPERSEDE：旧 Evidence 按原生命周期 SUPERSEDED；新事实有本次 origin snapshot，不能称 retain |
| 已认证删除或完整重新观察 scope 内不再出现 | INVALIDATE：原 Provider 自己的支持 INVALIDATED；不能只因某输出没有事件就退休超出已验证 scope 的支持 |
| 同一 `(factType,providerId,providerFactId)` 出现多个 ACTIVE origin 或缺失 R009 原候选 | 拒绝歧义/不完整历史，不能取最新或用 winner 回填 |
| 其他 Provider 对同 FactKey 的支持仍有独立有效依赖 | 保留其原支持；Native support 退出不等于整个 Canonical fact 删除，原 selector 重新选择 |
| 其他 Provider 的依赖 Source 已改变/删除，或没有可认证依赖证明 | OTHER_PROVIDER_REVALIDATION_REQUIRED；不自动退休他人支持，也不保留为“当前有效”，不提交半张图 |

**Provider fact 退出与 Source 文件删除是不同事件。** “Native 不再支持但另一 Provider 仍支持”的正例必须使另一支持的完整依赖仍有效；不能拿一个指向已删除 SourceFile 的旧证据当 surviving support。

新观察调用原 collectMergeSupports，只提交本次一份成功 Native snapshot；历史支持从可信捕获中加载并逐项验证，不包装为另一次 Native observation。完整合格 support 集合使用原 selectMergedFacts / staged grouping 规则，保留悬空引用、冲突、最低置信度、稳定选择与其他 Provider 语义。不放宽 mergeCanonicalObservations 的唯一性检查。

## 6. Syntax、basis 和 coverage

未改变文件的原 wire Syntax 可以保持 origin；这不表示旧 Canonical SyntaxEvidence 的 SupportRef 可以原样适用新 Code basis。现有 assertSupportRefs 要求 exact basis/valueDigest，不能换 basis 字符串后直接认定有效。

后续 B1-C/D 必须在完整 Code/support 候选形成后，重新验证保留 Syntax 的 Source/owner/引用闭包及 extraction 契约，对照**最终** basis 构造/验证当前投影及 support；原观察、原采集时间和历史 Canonical 记录保留。当前投影若需要新记录，其身份/去重/不可变性及 R011 外键须在 B1-C 完整契约中定义。不修改旧 SyntaxEvidence payload 或为未观察内容伪造新 ProviderSnapshot。

coverage 区分“某 snapshot 观察了哪些文件”与“当前 activation 对完整 Source 的能力覆盖”。新局部 snapshot 只能声明自身 scope；当前完整 coverage 必须由 history 的每个 Source unit/group 的有效 coverage 来源组成，含零事实文件、完整 Source census 和所有 required facets，不能按 emitted node 数或 latest snapshot 近似。现有消费者若只读 latest snapshot/旧 v3 summary，不可自动视为已支持这种组合；C/D 需要明确接入或拒绝。

如果 basis 重新锚定、保留观察 provenance 或 membership 完整性在现有结构中不可表达，阻塞对应 Apply，交 governed amendment；不能把这一段解释为已批准的 Canonical Syntax mapper 或新的 SupportRef shape。

## 7. 真实历史、R011 与事务边界

B1-B1 的 pure draft 只能证明声明之间一致，不能返回 authenticated/ready/applicable 或历史 handle。未来独立 HistoryCapture 必须绑定同一个真实 SQLite connection/incarnation、有界读取和释放/失败永久失效；C3-A 现有 historicalSourceProof 保持 UNAVAILABLE。

新历史读集需包括 source manifest、membership、origin candidates/coverage、活动 Code/support digest、locator 和 current pointer。C3-A 公共 recheck 拒绝 ambient transaction，继续保留。Store 锁内复核要由 Storage 内部事务 owner 复用相同受控读集，不接收调用方的 inTransaction=true。

B1-C/D 必须确保：

1. R011 不猜测 backfill；旧 R010/已存在 mixed Code 没有历史时返回 FULL_ANALYSIS_REQUIRED，保留 last-good。若其他 Provider 也没有历史，单跑 Native 不能自动授予那些支持真实性；需要相应 Provider 的有效重验证或其既有授权撤销流程。
2. 只有联合成功提交才能建立/替换活动 history pointer；历史 Source manifest 副本、Code、Evidence/candidate、Syntax/support、snapshot、coverage 与 history pointer 一次提交。当前 Source service 仍可按既有 validated CAS 独立推进；联合 Store 只重查目标，不将当前 Source 回退到旧历史，也不强迫每次 Source 扫描与 Code 激活同事务。不能先写 history 再依赖将来 Apply 补齐。
3. 任何旧 writer 改变 Code/support/coverage/指针但未维护新 history，后续完整重查必须判历史不再适用，不从新状态重算 hash“修好历史”。该失效检测须覆盖相同 WORKTREE/fingerprint 下的支持变化。单独推进 current Source 产生新的 target 差分，不会把仍绑定旧活动 Code 的不可变历史改写成新事实。
4. 读取待退休的旧 Source-backed candidate 时，用可信旧历史验证原引用；允许其在 target 中不存在，只能用于明确受权退休，不能进入 retained 集合。新完整候选所有引用必须对 target 有效。不得放松旧 C3-A 或 Store 原有孤立引用检查。
5. 最终 BEGIN IMMEDIATE 内重查全部旧 basis/history/Source/support 与 stage 冻结身份，CAS 后一次提交；失败完整回滚，重启仍能验证 pointer/manifest/candidate 关系。close/rollback/rebuild/跨连接永远不复活 lease。

R011 仍是未发布 framework_syntax reservation；物理表、PK/FK/索引、升级/备份/恢复与 manifest checksum 在 B1-C 写全并评审，本轮无 SQL。不增 R014、不修改 R001..R010，不提前依赖 R012/R013 或 workspace compilation 表。

## 8. 错误与安全边界

拟议可区分状态：INVALID_HISTORY（结构/关系错误，不能当作可重建的正常缺失）、HISTORY_UNAVAILABLE、HISTORY_CHANGED、FULL_ANALYSIS_REQUIRED、OTHER_PROVIDER_REVALIDATION_REQUIRED、RESOURCE_LIMIT_EXCEEDED，以及 TRANSITION_DRAFT/NO_OP_DRAFT。具体 API/code 字符串随书面接受后的实施计划固定，不是现有协议新增错误。

不引入时间 TTL/“最新 N 次”启发式或新默认预算；原限额和明确提供的读取/对象/序列化控制保留。digest 做一致性绑定，不能给 caller scalar、文件、旧 mutable DB 或导出包生成 Storage ownership。错误不回显 SQL、原路径/Source、payload 或环境；没有重试到绿、自动全量、校准或云端 fallback。
