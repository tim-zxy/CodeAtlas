# P05-W2-002 File and Worktree Fingerprints Design

Date: 2026-09-24
Task: P05-W2-002
Status: written design for user review; no implementation authorized by this document

## Purpose and authority

Make the selected source-file inventory comparable across process restarts without treating a mutable worktree as an immutable commit or activating a code graph. Success means a real repository SQLite database can retain one current `WORKTREE` observation, a later process can detect changed paths from fresh file bytes, and a failed observation or transaction leaves the prior observation intact.

This design implements P05-W2-002 in [WORK_BREAKDOWN](../../handoff/WORK_BREAKDOWN.md) and its restart/worktree mapping in [DESIGN_TRACEABILITY](../../handoff/DESIGN_TRACEABILITY.md). [CANONICAL_IR](../../handoff/specs/CANONICAL_IR.md), [RUNTIME_CONFIGURATION](../../handoff/specs/RUNTIME_CONFIGURATION.md), [SQLITE_SCHEMA](../../handoff/specs/SQLITE_SCHEMA.md), [SECURITY](../../handoff/specs/SECURITY.md), [EVALUATION](../../handoff/specs/EVALUATION.md), and ADR-001/002/003/004/011/012 govern it. The prior [P05-W2-001 design](2026-09-24-p05-w2-001-repository-discovery-design.md) remains the scanner contract. No FROZEN decision, published migration, Canonical IR schema, or numeric gate changes here.

## Scope and chosen approach

The `source` package extends the selected-file observation path with streaming byte hashes, byte counts, and a deterministic inventory fingerprint. It owns no SQL. The `storage` package reads and atomically replaces the repository's current source observation using existing R001/R002 tables. A narrow application use case composes scanning, fingerprinting, and a storage port; the runtime may call that use case on startup after database migration. The production CLI and background watcher remain later tasks. Integration tests exercise the same use case with a closed and reopened SQLite database, rather than claiming that the still-unimplemented product startup path invokes it.

Using a caller-supplied old in-memory snapshot alone would not prove restart correctness. A JSON sidecar would create a second local authority outside SQLite. Both were rejected in favor of the existing repository database. This task adds no generic VCS framework and does not extend non-Git scanning. It does not perform the P05-W2-010 added/modified/deleted/rename classification, Native REFRESH, graph patch, Knowledge compilation, or RevisionSet freeze.

## File and revision contracts

Only files selected by the approved P05-W2-001 policy are fingerprinted. Their paths remain validated `RepositoryRelativePath` values with `/` separators and deterministic sort order. A file observation carries the existing language hint and orthogonal classification, plus `contentFingerprint` and `sizeBytes`. `sizeBytes` is a non-negative safe integer representing raw byte length. File content fingerprints use lowercase `sha256:<64 lowercase hex>` over unmodified file bytes; an empty file has the standard SHA-256 of the empty byte sequence. No line-ending conversion, Unicode normalization, Git blob hashing, or text decoding affects the hash. The implementation streams bytes with bounded buffers and verifies the opened file's identity and metadata before and after reading. A detected disappearance, type replacement, or metadata race is a typed failure, not an omitted file or partial success. The scanner does not claim an atomic filesystem snapshot when a file changes after its own observation; the next reconciliation detects it.

The worktree content fingerprint uses lowercase SHA-256 with a distinct version/domain prefix and unambiguous length-prefixed UTF-8 fields. It processes selected entries in canonical path order. Each entry contributes path, content fingerprint, size, language hint, role, provenance, and content kind. The worktree fingerprint therefore changes when selected contents, selection, or analysis-relevant classification changes. It is independent of walk order, native path separators, Git branch label, commit display text, timestamps, and assigned opaque IDs. Hashing all selected files on reconciliation is intentional for this correctness-first task; metadata-only cache shortcuts and adaptive scheduling need separate measured evidence.

The R002 `revisions` table holds one current `WORKTREE` row for this repository. First observation allocates an opaque EntityId; subsequent observations reuse it and may change its content fingerprint as allowed by `validateRevisionTransition`. If no worktree row exists, insert one; if more than one exists, reject ambiguous state instead of choosing arbitrarily. A `baseRevisionId` is set only when an already persisted COMMIT revision in the same repository corresponds to the observed HEAD; otherwise it is `null`. The Git HEAD string is not itself an EntityId. A changed HEAD does not regenerate the worktree ID. This task does not create COMMIT or SNAPSHOT revisions.

Each accepted path gets an opaque SourceFile EntityId. The adapter reuses the prior ID for the same repository-relative path, even when content changes; a new path gets a new ID. Removed paths are absent from the current worktree's `source_files` rows. A later re-add may receive a new ID; rename tracking is not inferred. IDs are never hashes or paths in disguise. The persisted SourceFile's `revisionId` is the stable worktree ID, and its sensitivity defaults to `INTERNAL` for selected ordinary source. Existing secret-path denials still apply. This default grants no remote LLM, embedding, or transport permission; those remain separate policy decisions. A future finer sensitivity policy requires its own reviewed design.

R002 has no file-size column. Size is returned in the observation and included in the worktree fingerprint, but is not separately persisted. Path and content fingerprint are sufficient for restart comparison. Published R002 SQL and checksum are not modified, and no new migration is justified by this task.

## Reconciliation and atomicity

The application use case obtains the last committed worktree fingerprint and path-to-ID/fingerprint mapping, runs the Git scanner and file observation, and computes a sorted set of paths whose selected-state fingerprint differs. A path present on only one side is in that set. The set has no `ADDED`/`MODIFIED`/`DELETED` label; P05-W2-010 owns those event semantics. Changes to excluded files do not enter the set. An initial observation returns all selected paths; an identical later observation returns an empty set. The result includes the validated `WorktreeRevision`, observed file sizes, and changed paths without raw file bytes.

After the complete observation succeeds, storage opens one write transaction. It re-reads the current fingerprint under the write lock and rejects a stale baseline if another reconciliation committed since the initial read. It then validates repository/revision identity, updates or inserts the WORKTREE row, replaces current worktree `source_files` rows with validated selected entries, and commits as one unit. SQLite errors or validation failures roll back the entire new observation. Failure never advances `repository_state.indexed_revision_id` or removes the last good graph. The application must not infer graph freshness from revision ID alone: a provider snapshot's requested fingerprint must match the current worktree fingerprint before its facts are considered current. Graph activation and stale-fact handling remain P05-W1-010/011 and P05-W3-020 responsibilities.

No database transaction is held during filesystem traversal or hashing. The pre-commit baseline check protects against competing database writers, not an atomic OS-wide filesystem snapshot. If the filesystem changes after observation, another reconciliation is required. A failed scan, including a symlink or security-policy violation inherited from P05-W2-001, never writes any new rows. Public diagnostics carry safe operation/path information but no source bytes, hash inputs beyond published fingerprints, secrets, Git output, or unrestricted environment values.

## Fixtures and verification

Add version-1 manifests under `fixtures/source/` for a pinned `worktree-fingerprint` case and a `restart-reconciliation` case, with explicit setup and expected artifacts. The first pins raw-byte SHA-256 values and the inventory fingerprint for an empty file, a UTF-8 Java file, a binary file explicitly selected by policy, and a file larger than one read buffer. It proves canonical path ordering, stable repeated output, same-size/different-byte sensitivity, and classification/selection sensitivity. The second uses a real temporary Git repository and migrated repository SQLite database: observe, close, reopen, observe unchanged, modify, add, delete, reopen again, and compare exact sorted changed-path sets and stable retained IDs. It verifies ignored changes do not enter the set and no COMMIT or SNAPSHOT row is invented.

Focused tests also inject a file disappearance/type change, read error, database write failure, and competing baseline update. Each failure must leave the previous persisted fingerprint, file mapping, and indexed graph pointer intact. Tests verify the `WORKTREE` transition validator, `SourceFile` schema boundary, first-observation behavior, ambiguous multiple-worktree rejection, malformed stored rows, and `baseRevisionId: null` when no matching persisted COMMIT exists. A fixture may use declared exact hashes and paths; it must not introduce an unapproved numerical performance threshold.

Before claiming P05-W2-002 complete, run its focused tests and both declared Fixtures, the full applicable TypeScript/Rust/architecture/format gates, and failure/recovery checks. Record exact commands, counts, fixture IDs, schema/migration impact, limitations, revision, and next task in `CURRENT_STATUS.md`; update its traceability row with actual executable paths. Hosted clean-install CI is required before integration is considered complete. The implementation plan must first inspect the existing storage runner and source test helpers, and preserve all prior P05-W2-001 Fixture results.

## Change control and exclusions

No new SQLite migration, Canonical IR or IPC field, remote access path, provider execution, Java parser, graph activation, watcher, product CLI command, semantic Knowledge update, or frozen RevisionSet is added. If implementation shows R002 cannot safely represent one mutable worktree observation, stop and propose a governed ADR or Design Change Proposal rather than altering published SQL in place. EVOLVABLE performance or cache adjustments require pinned Fixture/Evaluation evidence and synchronized authorities. The existing Phase 0.5 exit gates remain unchanged.
