### 4.3 ProviderTarget / 引用与歧义

引用表来自完整原支持/候选映射，不只来自 winner 或“碰巧已有 owner 的节点”。键是既有 typed ProviderNodeRef；值须对应最终 selected CODE_NODE。每个 resolved target 和 unresolved candidate 都必须可映射，否则原子拒绝，不丢候选、不补节点。

- Callee RESOLVED → state=RESOLVED、target=精确 ScopedRef、candidates=[]；不升级 raw HEURISTIC 为语义上 EXACT。Canonical Callee 本身没有 resolution 字段，这个表示限制必须在原 raw 观察/策略方法依据中保留，不能声称无损保留了该字段。
- Callee UNRESOLVED → state=NON_RESOLVED、target=null、全部可映射候选；按既有 ScopedRef key 排序去重。即便去重后只剩一个 Canonical 候选，也保持 NON_RESOLVED。
- SyntaxValue REFERENCE 的 name 原样；RESOLVED 保留 EXACT/HEURISTIC 和一个候选；UNRESOLVED 保留 AMBIGUOUS/UNRESOLVED/UNSUPPORTED 及其候选约束。
- 特别拒绝：raw AMBIGUOUS 的两个不同 Provider refs 归并后不足两个不同 Canonical refs 时，Canonical SyntaxValueSchema 无法保留 AMBIGUOUS；返回 INCOMPATIBLE_CONTRACT，不静默改为 EXACT、UNRESOLVED 或 UNKNOWN。此拒绝不必扩展 IR；若未来要求其他表达，另走治理。
- unsupported 仍为空候选；Source/owner/嵌套引用都必须同 repository/revision。不能把未解析名字查字典后自动宣称已解析。

原 ProviderTarget.originalHint 在 Canonical Callee/Value 中没有同名字段；不擅加额外 IR 字段，也不覆盖 name。原 raw 输入与 request/output 身份继续作为上游原观察依据保留；本附约不设计新的 raw 持久化库或冒充 H5 资格账本。

## 5. syntaxKey 与身份分工

提议版本化规则：

`payloadDigest = historyDraftDigest(keyMeaning, existingExplicitLimits, sharedCompositionBudget)`

`syntaxKey = digestIdentityTuple('syntax-key-v1',[repositoryId,sourceFileId,sourceFingerprint,startLine,startColumn,endLine,endColumn,syntaxKind,payloadDigest])`

keyMeaning 为上述已完成映射的 owner+payload；其中每个 ScopedRef 在身份投影中只表示 typed Canonical CODE_NODE id，不带当前 revision/basis。只投影已知引用位置，不任意剥除 OBJECT 用户值里的 id/revision 字段。candidate 集合先按规范化引用排序去重；有意义的参数/ARRAY/OBJECT entries 顺序保留。

该规则不包含 providerId、providerSyntaxId、ProviderSnapshot、requestId、时间、confidence、extractionVersion、当前 Code digest、最终 projection id。Canonical node id 已由现有 factKey 身份规则产生，不能替换成 Provider ref 或展示名。相同最终 Code/Source/语法在不同 Provider 声明下应得到相同 key；Source 指纹/位置/语义改变应改变 key。不承诺移动文件或修改后保留逻辑身份，不引入跨文件语义 identity matching。

复用 Providers 的 historyDraftDigest 及 identity-tuple，**不能从 Providers import Storage 的 H1 encoder**。historyDraftDigest 的既有 UTF16 对象 key 顺序保持不变；旧 C3-A SQL binary encoding 和 ownerMap encoding 各自保持原样。新域标签是待批准身份契约，不是新数值门槛。需独立 Unicode、数字对象key、delimiter/空值和 Provider更换 goldens 后才能实现。

origin 仍绑定最初 snapshot/Source/providerSyntaxId/initial Canonical envelope；current projection 只重新构造 finalbasis supportRefs/id，不能覆盖原 confidence/extractionVersion/payload。Source/mapper/policy 契约变化需要重新观察/创建新 origin 或显式 retire，不以“重投影”为由改旧 origin。

## 6. Confidence：本次不选择任何数值

置信度要说明“这条 Syntax 观察及其支持如何获得”，不证明框架业务语义或实际运行行为。需要分别识别语法类型、抽取版本、owner 有无、Source 对应、callee/reference resolution、UNKNOWN/动态表达式以及支持闭包；Source/引用缺失是拒绝，不靠降分掩盖。

获准策略必须是固定的版本化规则，明确适用 extractor/mapper/IR 契约、输入分类、输出 score/method/reasons、独立 Fixture/Evaluation 证据和用户批准。不是任意 caller JSON、用户配置或 Plugin callback；policyVersion/摘要仅标识契约，不认证运行或免除资格。

本轮只提出分类、证据与阻断规则，不填写任何 score，不采用0/1默认值，不计算新聚合权重或阈值。Code confidence、旧结构 IR Fixture 中的合法 confidence 和 H1 的示例 Canonical Syntax 均不是新映射策略的测量依据。无owner ARTIFACT 需自身证据，不能拿不存在的 owner 分数填空。

数值门禁需要的审查材料：固定且独立的 Source/annotation/expectation；代表性正例、无owner、动态值、歧义、unsupported/partial与失败控制；按类型/解析状态报告提取和支持一致性；解释分数的语义与局限；候选值及其证据、明确用户批准。是否需要实际观察或校准以及操作范围另案确认，不因本附约而自动运行。不得把取消/未执行的检查写成通过。

**门禁**：不存在已接受且适配当前契约的数值策略时，新 Canonical Syntax 映射返回 INCOMPATIBLE_CONTRACT；不输出残缺 SyntaxEvidence、不解锁 H3/H4/H5、不发布 Canonical/Knowledge。原始Code图与H1历史仍可读取。支持纯 raw/owner/scope 的局部组件计划可以单独提出，但不得称其为完整 H2 或完整映射验收。
