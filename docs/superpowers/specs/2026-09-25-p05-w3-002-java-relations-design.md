# P05-W3-002 Java Relations Design

Date: 2026-09-25
Task: P05-W3-002
Status: written design for user review; implementation is not authorized by this document

## Intent and authority

Continue the integrated P05-W3-001 Java SYMBOL path with source-grounded imports, calls, inheritance, and initial references. A Java repository's approved SourceFile inventory must yield deterministic ProviderEdge facts through the existing Native IPC v1, including honest ambiguous and unresolved targets. Success is the four declared relation Fixtures, the existing Critical Direct Call Precision (at least 95 percent) and Recall (at least 90 percent) gates, and bounded/failure-safe protocol behavior. This task does not complete Phase 0.5 or activate Canonical State.

The governing authorities are `docs/handoff/WORK_BREAKDOWN.md` (P05-W3-002), `PHASE_ACCEPTANCE.md`, `DESIGN_TRACEABILITY.md`, `specs/CANONICAL_IR.md`, `specs/NATIVE_IPC.md`, `specs/PROVIDER_SPI.md`, `specs/EVALUATION.md`, `specs/SECURITY.md`, `specs/RUNTIME_CONFIGURATION.md`, ADR-002/010/012/014, and `docs/specs/native-analyzer-scalability.md`. The P05-W3-001 design and merged implementation are the baseline. No new FROZEN schema, IPC version, migration, numerical gate, language, or framework capability is proposed.

## Baseline and design choice

The Rust Java adapter currently returns only `SymbolFact`, diagnostics, and syntax coverage. The analysis coordinator accepts only `SYMBOL`, emits `NODE` but no `EDGE`, and drains at most one bounded worker batch at a time. The TypeScript Native client already validates `EDGE` as a strict `ProviderEdge` and checks complete-stream counts, context, checksum, and terminal integrity. Existing Java Fixtures pin exact SYMBOL nodes; no relation Fixture has been checked in. The Phase 0 evaluator's executable CLI knows six generic node/edge/critical-fact gates, not `callPrecision` or `callRecall`, despite those names appearing in the Evaluation specification's future Java example.

Three approaches were considered. File-local-only resolution preserves one parse but leaves straightforward cross-file calls and inheritance unresolved. Retaining all ASTs or full file results enables one parse but conflicts with the bounded-memory policy. The selected approach is a bounded two-pass full `ANALYZE`: build a compact repository declaration index, then re-read and parse each file to emit facts and resolve relation sites against that index. It trades extra parse work for complete cross-file candidate visibility without retaining ASTs or unbounded results. Resource exhaustion is a typed failure, not silent fact omission. Cold/refresh performance baselines remain assigned to P05-W9-001 and P05-W3-020; this design does not claim a latency target.

## Components and data flow

The core coordinator retains request validation, safe source access, worker scheduling, cancellation, output budgeting, event order, and JSONL emission. Java-owned extraction classifies grammar nodes into declaration records and relation-site records; a repository resolver uses only Java language facts and bounded indexes to select zero, one, or multiple candidate ProviderNode IDs. A small emitter maps those records to existing strict `ProviderNode`/`ProviderEdge` payloads. Framework annotations may be recorded as syntax references only; no Spring or other framework meaning enters the adapter or resolver.

Pass 1 reads and fingerprints every requested eligible Java file through the existing source-access boundary, parses its symbols, and stores only the bounded declaration index needed for name/scope/signature lookup. It discards each AST and does not emit NODE/EDGE facts. Pass 2 reopens and verifies each source against the same request fingerprint, parses it, and emits source files, symbols, relations, coverage, and diagnostics in request-file/source order. A changed, disappeared, unsafe, or over-budget source in either pass ends with an existing typed failure terminal; no completed stream is returned. The coordinator accounts index memory in the request's `maxMemoryBytes` alongside worker reservations and bounded results. It does not widen IPC line/event/total-byte limits, add a second worker knob, or buffer the whole repository's relation results. Backpressure remains at the existing JSONL writer; downstream staging is a later task.

The full-analysis request explicitly asks for `SYMBOL` and the desired relation capabilities. Each supported requested capability yields per-file `COVERAGE`, including a valid zero-fact result. Existing syntax-error `PARTIAL` diagnostics/outcome remain. The richer eligible/covered/resolution statistics and complete outcome matrix belong to P05-W3-003. The descriptor advertises an additional Java capability only after its declared Fixture and gate evidence passes; a descriptor string alone never upgrades maturity.

## Provider Fact semantics

Every relation is a `ProviderEdge` with `providerKind` in `java.import`, `java.call`, `java.inheritance`, or `java.reference`, the same snapshot/repository/revision as its source node, a source-grounded relation-site `SourceRange`, and a `ProviderTarget` in the existing `RESOLVED` or `UNRESOLVED` shape. Exact resolution requires one defensible declaration match. If only incomplete language evidence supports a single candidate, label it `HEURISTIC` rather than `EXACT`; a tie has `AMBIGUOUS` with at least two stable, unique candidate references; no defensible target uses `UNRESOLVED` with an exact, bounded, source-spelled `originalHint`. External JDK/dependency targets absent from the requested inventory remain unresolved; the analyzer does not invent nodes or interpret a wildcard as proof that a particular declaration exists. `UNSUPPORTED` has no candidates. Candidate order is deterministic, never worker-completion order.

The import source is a file-scoped ProviderNode of kind `java.compilation_unit`, named by the repository-relative path, with a stable path-derived ID and nullable range. This node is emitted only when `IMPORT` is requested, so the existing SYMBOL-only goldens stay exact. Normal and static single imports resolve to an indexed type/member when uniquely present. Wildcard imports target the indexed package/type container when present, not every member it might contain; absent containers remain unresolved. Import edges use the import-name range and retain static/wildcard distinctions in the provider-specific kind where needed. Canonical normalization of this node and these edge variants is assigned to P05-W4-001; this design does not prescribe a new Canonical kind.

Calls originate from the enclosing declared method or constructor and target a declared method or constructor. P05-W3-002 covers unqualified direct calls, `this` calls, type-qualified static calls, and `new`/`this(...)` constructor calls within such bodies. It uses lexical owner, explicit receiver, same-package/import information, and source-spelled arity/signature evidence. It must not turn matching arity alone into an exact overload selection when argument types are insufficient. Calls with several plausible overloads remain `AMBIGUOUS`; absent or external targets remain `UNRESOLVED`. Calls in initializers or other contexts without a safely identified caller are not assigned to a made-up method; the coverage/diagnostic path records the limitation. `super` calls and dynamic dispatch beyond this initial direct-call set are not silently declared exact.

Inheritance originates from a declared class/interface and uses the `extends`/`implements` type-use range. Initial references cover syntactic type uses, non-call field access, and method references with a defensible source owner. A syntactic invocation is a `CALL`, not a duplicate `REFERENCE` for the same site. Type/member syntax without adequate owner or target evidence remains unresolved or partial; the language adapter does not infer framework, runtime, or business relationships. Non-call `REFERENCE` and `INHERITANCE` resolution follow the same candidate honesty rules as calls.

ProviderEdge IDs use a new domain-separated `java-relation-v1:` SHA-256 over unambiguously length-prefixed repository-relative path, relation kind/variant, stable source ProviderNode ID, source-spelled target hint, relation-site byte position, and an occurrence ordinal for otherwise identical sites. They never incorporate worker completion order, snapshot ID, or a guessed target. Target-resolution changes therefore change payload, not site identity. A source edit that moves a relation site may change its ID; P05-W3-020 governs patch/stale-fact behavior. Source ranges retain zero-based UTF-8 byte coordinates. New IDs and payloads are pinned by goldens.

## Fixtures, metrics, and errors

Register `java-call-basic`, `java-overload`, `java-inheritance`, and `java-unresolved-call` under the existing Fixture Manifest v1 with checked-in source trees and exact expected ProviderNode/ProviderEdge, coverage, and diagnostic goldens. Cases must include normal/static/wildcard imports; same- and cross-file direct/this/static/constructor calls; extends/implements; type/method/field references; competing overloads; unknown external targets; and source-order/worker-count determinism. The manifest's `criticalFacts` identify the labeled direct-call sites. Do not assign unimplemented `callPrecision`/`callRecall` names to the current six-gate CLI and claim they ran.

A task-local Evaluation check reads the registered Fixture goldens and the real-binary Native client result, matches labeled direct-call sites and their expected target state/reference, and reports TP/FP/FN, precision, recall, and unmatched examples. A wrong resolved target counts FP plus FN; missing or non-resolved output for an expected resolved direct call counts FN; an extra resolved direct call counts FP. Unresolved/ambiguous goldens are also checked exactly and reported separately, so they cannot be converted to invented resolved calls to improve recall. The declared existing thresholds are compared without rounding. The check does not rewrite the Phase 0 generic evaluator or lower a gate; if executable gate semantics prove incompatible with the governing Evaluation design, stop for reviewed design synchronization before claiming acceptance.

Focused tests cover per-kind extraction and identity; overload ambiguity, unresolved/external targets and deterministic candidate ordering; multiple files/workers and completion orders; source mutation between passes; syntax partial and zero-relation success; memory/event/byte/deadline exhaustion; checksum, terminal counts, stdout/stderr separation, and no applicable partial stream on failure. Run the declared Rust and real-binary TypeScript suites, Fixture registry/goldens and task-local call metrics, repository build/test/format/architecture checks, and hosted clean-install CI. Record exact commands, results, resource limits, coverage, residual gaps, and implementation revision in `CURRENT_STATUS.md`; replace the generic P05-W3-002 traceability row with actual paths and evidence.

## Exclusions and governance

No REFRESH, changed-file invalidation, Canonical FactKey computation, normalization, SQLite apply, Knowledge, Wiki, Diagram, Agent API, new language, or framework semantics is added. Full P05-W3-003 coverage statistics and Phase 0.5 Worker Consistency/staging/performance exit remain separate. Prior SYMBOL-only Fixtures must remain unchanged and pass. If a FROZEN Provider/IPC/IR contract cannot express a required fact, stop for ADR or Design Change Proposal; do not silently extend strict shapes. EVOLVABLE resource or capability policy changes require pinned Fixture/Evaluation evidence and synchronized controlling documents.
