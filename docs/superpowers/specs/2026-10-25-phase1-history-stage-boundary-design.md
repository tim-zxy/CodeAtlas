## 3. 联合数据与权限契约

### 3.1 四种对象分别承担什么

1. **声明候选 DTO**：现有HistoryTransitionPacket、DeclaredDeltaSupportCandidate等纯数据；可序列化、可伪造，只能证明一致性。现有 public/private 函数语义不变。
2. **历史捕获 handle**：未来Storage私有、不可序列化的同连接/同incarnation能力，绑定已提交的history pointer、不可变manifest及完整读集。view用于诊断/派生，不代表权限；JSON往返、跨连接、close/reopen后都不能重建。
3. **临时 owner-stage handle**：证明本次目标Source、观察scope、可用Java节点映射及相关契约属于本次受控准备阶段。stageDigest是其结构身份，不是最终Code digest；不包含尚未得到的Python结果或最终Syntax，避免循环依赖。
4. **最终冻结 stage lease**：完整Code/support/coverage、最终RepoBasis、Syntax投影/支持、历史转换与相关读集验证完毕后，Storage私有状态机授予的一次性Apply资格。不能由前三者的摘要拼出。

前三者与最终lease的精确字段/函数签名、私有所有权注册、释放和错误代码需要在下一份完整契约冻结。本文不创造可直接实现的临时API或默认限额。

### 3.2 历史记录与捕获读集

沿用ActivationHistoryRecord逻辑契约：activation/parent、repository/revision、最终RepoBasis、完整Source manifest（含OTHER/零事实项目）、契约/依赖单位、所有活动支持的原candidate与Evidence关系、origin snapshot/coverage、Syntax原观察与当前投影、观察scope和资格引用。

- 历史Source用于验证旧引用和明确退休；目标Source用于验证所有保留/新增候选。不能用目标缺少旧文件为理由让旧历史不可读，也不能让待退休旧引用混入保留集合。
- 保留Evidence原origin/time/snapshot和原candidate；当前membership单列。支持及coverage变化即使WORKTREE/fingerprint不变，也必须使旧captured读集过期。
- Code activation digest与历史/关系摘要分开；不重新定义现有C3-A和owner-map编码。摘要输入不包含自身digest、root或DB路径。
- Source service仍可独立validated CAS前进；不回退Source，不把Source扫描强行与Code激活绑成一笔事务。
- 现有C3-A继续R010/UNAVAILABLE契约。新history读取不能悄悄放松它的Source/孤立引用检查；应先给出新历史路径的读计划及共同复用部分，再决定最小新增模块。

**缺历史的处理必须真实：** R010旧库与历史失效库的增量路径返回FULL_ANALYSIS_REQUIRED并保留last-good。首次历史只能由经过验证的联合全量建立；单跑Native不能授予其他Provider旧支持的新真实性。全量Native-only可建立哪些状态、存在foreign支持时如何要求相应Provider重验证/既有撤销，必须有正负Fixture。不得从当前表“猜测回填”。

### 3.3 原始增量桥接

新增增量路径的责任是把已验证的本次Java/v5观察映射成**一份新Native观察**，再调用已存在的完整候选规则，不能直接写Canonical或Store。

- scope由可信历史与完整目标Source差分派生：Python按文件，Java按完整投影组，删除按历史证明。未观察部分只能保留已验证旧支持与旧coverage来源；不能对全仓盖本次COMPLETE戳。
- 请求/输出采用原校验器拥有的字节快照及身份；parsed Java v2保持PARSED_V2来源，不冒充原始传输checksum。metadata声明的时间/settlement不是实际子进程资格。
- 本次raw事实、provider refs、规范化candidate、typed-ref依赖映射、单位/coverage必须精确对应；不按ProviderFactId前缀、null range或selected winner反推依赖。
- 一个Provider本次最多一份新snapshot；NO_OP/仅删除等无观察路径不制造空snapshot。历史registry允许多个旧origin，不伪装成多个本次观察。
- PARTIAL/FAILED/CANCELLED不能通过重命名、重封checksum或裁掉不完整事实变成SUCCEEDED。真实运行未获授权/未合格时，生产路由仍拒绝。
- 输入复制、解码、规范化、历史规则及输出预算要组合成可核验的累计账本；现有各入口旧边界保持，不能给每阶段重新发满额度。完整计划必须明确已有计数的传递/重复表示收费和exact/one-below测试，不新造profile或数值门槛。

### 3.4 owner → 最终basis → Syntax

建议受控流程：可信历史/目标capture → Java完整组观察（若需要）及owner准备 → v5局部Code/Syntax观察 → 全部retained+fresh Code候选组装 → 计算最终Code/support basis → 对原/新Syntax重验证并构造当前投影 → 最终冻结 → 锁内CAS/联合提交。

临时owner identity在v5请求前必须可构造；最终Code digest只能在Python新Code、所有保留支持、选择器结果齐备后计算。两者不互相哈希。Java owner必须对应本次或合法保留的具体Java候选；Python输出owner必须对应同一严格stream的节点、Source与完整性证据。最终owner还必须对合并后的Code闭包有效。

原Syntax观察及旧Canonical记录保持历史不可变；当前投影如需新记录，必须设计其ID、去重、finalbasis绑定、retirement与FK，不改旧payload伪造重新采集。非owner型配置Syntax也要按自身Source/契约/最终basis规则验证，不能因为owner为空跳过。

### 3.5 冻结、Apply与故障恢复

- 新Stage应有明确的准备/owner已冻结/最终已冻结/已消费或失效状态。精确状态名可在完整设计确定，但每条mutation路径必须有状态门禁；普通completed或旧v3 seal不是最终冻结。
- lease绑定真实connection、incarnation、Stage实例和不可重建的owner状态。close、失败/rollback、重建、跨连接以及成功消费后不可复活；最终冻结后事件、规范化、supports、coverage、Syntax、摘要与所属上下文全部拒写。
- Store自行取得BEGIN IMMEDIATE，锁内读取并比较Code/support/coverage、Source目标、history pointer/manifest、契约、Stage冻结身份。公共capture recheck保持拒绝外部事务；内部复核由Storage事务owner调用受控读逻辑，不接受inTransaction=true之类caller声明。
- 一次提交Code、R009候选/Evidence关系、Syntax/support、snapshot/coverage、历史manifest/成员、活动指针。旧Source不回写。失败完整回滚；实际重启后验证同一last-good，而非仅在内存对象上断言。
- 旧writer未维护新history时必须可检测地失效；不能读取新状态后重算hash修补旧manifest。完整设计须覆盖全部旧full/patch/native writer与reader兼容，不能只封一个入口。
- lease消费时机、提交失败后的失效、磁盘失败/进程退出后的持久恢复、旧R010summary显式不兼容行为，都必须在事务故障矩阵逐项定义。

## 5. 治理、待决策与Exit

本提案拟作为ADR-020下的联合细化DCP。接受方向后，完整设计需同步Canonical IR原origin/当前membership说明（不改shape）、Provider SPI、Native scope、Security、SQLite/R011、Evaluation、scalability、WBS/acceptance/trace/status及上位B1设计。未批准前只在CURRENT_STATUS登记提案，不把推荐内容写成已生效契约。
