# P05-W1-010 Full Analysis Apply Design

Status: accepted by user for implementation planning on 2026-09-29. The conversational choice of bounded staging and the additive activation-fingerprint migration was confirmed on 2026-09-29; this document alone is not implementation approval.

## Intent and scope

Deliver a validated, bounded full-`ANALYZE` path from the Native JSONL stream through Canonical normalization and FactMerger to repository SQLite. A successful run replaces one repository's active Code graph in one activation transaction. Any failure leaves the previous graph and its activation metadata intact. A retained graph may be stale relative to a mutable `WORKTREE`; readers must be able to distinguish that state.

This is P05-W1-010, not `REFRESH`, patch apply, graph query, CLI, Knowledge, or a new numeric performance gate. Phase 0 remains closed. Existing protocol v1/v2 wire shapes, Canonical IR, FactMerger selection policy, and Rust's no-SQLite boundary remain unchanged.

## Current implementation evidence and the design gap

- `packages/providers/src/native-client.ts` validates exact JSONL framing/checksum but retains `events` and raw records until completion. Its existing 10 MB/10,000-event ceilings are safety limits, not a bounded large-repository apply path.
- `packages/providers/src/canonical-normalizer.ts` requires a complete `ValidatedNativeResult` and builds all node pairs and a provider-node map before edges. `packages/providers/src/fact-merger.ts` returns full arrays. Neither is a streaming database writer.
- `packages/storage/src/source-state/repository.ts` already demonstrates `BEGIN IMMEDIATE`, compare-under-lock, and rollback for source-state replacement. There is no `CanonicalFactStore` implementation or Application full-analysis coordinator.
- R001 `repository_state` stores only nullable `indexed_revision_id`. R002 permits the same `WORKTREE` ID to change `content_fingerprint`; source reconciliation does so without changing the active pointer. Therefore revision-ID equality alone cannot establish graph freshness, including for a successful zero-fact graph. `ProviderSnapshot.requested_revision_fingerprint` records an observation but is not an unambiguous active-graph pointer.

## Activation identity amendment

Add repository migration **R008 `indexed_fingerprint`** after immutable R001–R007. It adds nullable `repository_state.indexed_content_fingerprint`. Existing rows with a non-null revision ID migrate with a null fingerprint because the historical active fingerprint cannot be proven from that pointer; the migration must not invent one. Consequently, until a new successful full analysis activates both values, such a legacy row is reported as `UNKNOWN` freshness, never `CURRENT`. The migration must preserve its previous graph and pointer. Because legacy rows must remain readable, the additive column cannot carry a table-level check requiring both fields to be null or non-null. The validated storage write path instead sets both values together in one transaction and rejects a new ID-without-fingerprint state. The migration tests cover empty state, legacy non-null pointer, rerun, and failure rollback. A fresh DB uses both nulls before any activation.

This is an additive design change to the planned migration sequence, not an edit to published SQL or checksums. Planned Phase 1 `R008 execution_graph` and `R009 runtime_flow` become `R009` and `R010` respectively before either is published. On written-spec approval, synchronize `SQLITE_SCHEMA.md`, `ROADMAP.md`, `PHASE_ACCEPTANCE.md`, `DESIGN_TRACEABILITY.md`, and migration/Fixture inventories before implementation. No Phase 1 table is brought into Phase 0.5. The migration is within the existing SQLite-authoritative FROZEN architecture; no Canonical IR or IPC decision changes. If review identifies a conflicting accepted ADR, stop and record a separate Design Change Proposal before implementation.

Design-change record for review: the changed decision is the **planned**, not yet published, R008/R009 Phase 1 numbering in `SQLITE_SCHEMA.md`; its authority is a normative specification below accepted ADRs. The evidence is the R001 pointer/R002 mutable-fingerprint mismatch above. Alternatives were a pointer without durable freshness (unsafe) and a fresh immutable `SNAPSHOT` revision for every run (more source/identity copying and lifecycle work). The chosen additive column requires an R008 upgrade and the Phase 1 numbering shift, but leaves existing SQL/checksums, IPC, IR, Provider APIs, and security boundaries intact. Tests must cover legacy unknown freshness and rollback; deployment rollback uses a pre-upgrade database backup rather than attempting to down-migrate a published schema. There is no new remote data movement or secret storage. Affected phases are 0.5 and planned Phase 1 migration naming only; the affected documents and Fixture inventories are named above.

For a current `WORKTREE`, freshness is `CURRENT` only when the stored activation revision ID equals the worktree ID **and** the stored activation fingerprint equals the current worktree fingerprint. A retained old graph with a different fingerprint is `STALE`; missing activation is `NOT_INDEXED`; a migrated legacy pointer with unknown fingerprint is `UNKNOWN`. Never serve `STALE` or `UNKNOWN` as current silently. These labels are application/read-model semantics, not new Canonical IR fields or a promise that P05-W1-010 implements the later graph-query API. For immutable revisions, the same ID/fingerprint pair is checked against their stored revision.

## Boundaries and data flow

1. **Application coordinator** selects a persisted Repository/Revision/SourceFile set and requests a full `ANALYZE` through the Provider client. It supplies the expected revision ID and fingerprint, invokes normalization/merging and `CanonicalFactStore`, and never writes SQL. This task covers one full Native observation; the merge boundary remains Provider-neutral and can accept multiple independently validated observations without changing identity or selection policy.
2. **Provider transport** retains the public buffered `executeNativeRequest` for existing callers and Fixtures. Add a full-analysis streaming entry that applies the same per-line, envelope, sequence, context, count, checksum, terminal, timeout, cancellation, and byte/event limits before declaring success. A bounded queue pauses stdout consumption when staging is behind. No raw Provider payload or stderr is stored in canonical tables. The terminal cannot expose staged facts to activation until exact-byte checksum and complete-stream validation succeed. Invalid post-terminal data, EOF, failure terminal, or process error discards the provisional stage.
3. **Temporary staging** uses connection-local SQLite `TEMP` tables for validated Provider events and normalization intermediates. It is provisional, not an active canonical graph or a new persistent migration. Prepared inserts and bounded batches drain the transport queue; stage storage may spill to disk, while in-process pending records remain bounded by the declared request/resource limits and downstream backpressure. Source-file/provider-node lookup and deterministic ordering use indexed staging reads, not an all-repository JS map. A zero-fact success still stages terminal/coverage metadata and can activate an empty graph.
4. **Normalization and merge** read staged facts in bounded, deterministic groups. Reuse the existing canonical identity and FactMerger selection rules; a streaming refactor must prove equivalence to `normalizeNativeAnalysis` and `mergeCanonicalObservations` on existing Fixtures, event permutations, and two-provider support. Do not implement a second scoring/resolution policy. Validate cross-row facts, revision and snapshot fingerprints, referenced nodes, Evidence/Binding relationships, and coverage/diagnostics before activation. Any duplicate or dangling identity fails the whole run rather than silently dropping a record. Explanations remain diagnostic/Evaluation output, not a new authority table.
5. **CanonicalFactStore** owns the only persistent write path. Under one `BEGIN IMMEDIATE` transaction, re-read repository state and source revision/fingerprint; reject a changed source baseline. Replace the target revision's active fact relations in FK-safe order, persist the validated new snapshot, nodes, edges, unresolved targets, Evidence, FactEvidence, Bindings, coverage, and diagnostics using prepared batched statements, then update both activation fields last. One commit activates the complete result. There are no per-fact transactions. If the target is the same mutable `WORKTREE` revision as the previous graph, deletion/replacement is still inside this transaction, so rollback restores old rows and metadata. For a different target revision, the previous graph remains historical and the pointer changes only at commit.

The stage and activation use one owned SQLite connection; `TEMP` data is not visible across connections. The storage implementation must enable and test foreign keys. External readers see only committed state. Transaction lock duration, stage size, and elapsed stages are measured; no unmeasured numeric performance target is invented.

## Evidence lifecycle and failure semantics

Full replacement must remove active bindings and `fact_evidence` links for superseded target-revision facts before replacing those facts; old Evidence remains `SUPERSEDED` for provenance, but no old binding may point to a removed or newly different fact. New Evidence is `ACTIVE` only with a valid snapshot and matching fact. This task does not persist a failed/cancelled observation; it reports the failure without changing canonical tables or activation metadata. A failure during validation, staging, SQL insertion, or final pointer update drops temporary state and rolls back the entire activation transaction. A process crash leaves only the prior committed active graph. The prior graph may be `STALE` after source reconciliation; preserving it does not assert freshness.

Only `SUCCEEDED` observations enter FactMerger and activation, matching the existing Provider SPI/FactMerger contract. A complete Native `ANALYZE` stream with `PARTIAL` outcome remains a valid observation for diagnostics, but P05-W1-010 does not activate any of its facts or replace the previous graph. Broadening partial-result publication would require a separate reviewed lifecycle decision.

The source-state reconciliation transaction remains independent. If it advances a `WORKTREE` fingerprint during analysis, activation's compare-under-lock rejects the stale result. The coordinator may request another full analysis later; it must not relabel old facts as current or mutate the source fingerprint backward.

## Verification and quality gates

- Extend the repository migration Fixture with the additive R008 path and exact schema/upgrade/rollback assertions; do not edit R001–R007 or weaken their checksums. Confirm legacy non-null pointers become `UNKNOWN`, not falsely `CURRENT`.
- Reuse Native protocol v1/v2 byte and real-binary Fixtures to compare buffered and staged streaming acceptance/rejection, including checksum mismatch, missing/extra terminal data, max-line/event/total-byte limits, timeout/cancellation, and backpressure under a deliberately slow stage consumer.
- Compare bounded normalization/merge output to the existing `canonical-normalization` and `two-provider-same-call` Fixture expectations, including reversed completion/event order, ambiguous targets, multiple supports, and zero-fact success. Include source-file and node references that arrive in an order requiring staged lookup.
- Inject failures before activation, during fact insertion, after old-row removal, and immediately before the activation-field update. Reopen the database and assert the exact previous graph, Evidence/Bindings, revision ID, and indexed fingerprint remain intact. Repeat when target equals the active mutable `WORKTREE` ID. A successful rerun must atomically replace graph and both activation values, with zero stale active bindings.
- Measure Cold Index and staged transport/normalization/DB-apply/total/peak-memory evidence under the existing Evaluation entry points. Record the observed baseline, not a fabricated threshold. The existing protocol ceilings remain explicit; a repository exceeding them fails safely rather than bypassing validation.
- Run package unit tests, registered Fixtures, architecture guardrail, root TypeScript/Rust/Native checks applicable to changed code, and hosted CI before claiming task completion. Update `CURRENT_STATUS.md` with fresh command/result evidence and the traceability row only after implementation gates actually pass.

## Exclusions and implementation planning gate

No `REFRESH`/patch apply (P05-W1-011/P05-W3-020), no change detector (P05-W2-010), no graph query/CLI, no Wiki/Knowledge/Agent projection, no adaptive scheduler, and no new numeric Quality Gate. Existing strict JSONL limits may constrain repository size; expanding them is a separate evaluated protocol/resource decision. This design is one vertical task but the implementation plan should sequence migration/freshness, streaming validation/staging, bounded normalization/merging, transaction activation, then failure/Fixture/Evaluation checks. The written spec requires explicit user review before an implementation plan or product-code change.
